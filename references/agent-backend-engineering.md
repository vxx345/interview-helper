# 大厂 Agent 后端工程 · 深度考点

题面涉及 Agent 系统的**工程实现**时读取本文件（编排、工具、失败、幂等、上下文预算、并发、多租户、评测、可观测、安全、成本延迟）。

> 与 `agent-interview-points.md` 的分工：
> - **本文件 = 工程实现层**（怎么把它做出来、做稳、做便宜）——面试官判断你「有没有真的做过」
> - `agent-interview-points.md` = **概念原理层**（是什么、为什么）——面试官判断你「懂不懂」

每个维度给出：**面试官真正在问什么** + **必答工程细节** + **量化/边界** + **高频追问**。

---

## 1. 编排与状态机

**面试官真正在问**：你会让模型自由规划吗？**生产系统里 90% 的问题都出在「让模型自由发挥」上。**

**必答工程细节**：
- **Workflow vs Autonomous**：人编排好流程、LLM 只做节点内决策（Workflow）vs 模型自主规划路径（Autonomous）。生产绝大多数是前者，或两者混合。核心判断：**任务路径是否可枚举**——可枚举用 Workflow，不可枚举才上 Agent。
- **自主度是旋钮不是开关**：用「允许的最大步数 / 是否允许跳出既定流程」来调，而不是二选一。
- **状态机显式化**：把流程建模成状态机/DAG，每个节点有明确入参、出参、失败转移。**不要让循环藏在 prompt 里**。
- **断点续跑**：长任务每步落 checkpoint（Redis / DB），失败可从最近一步继续，不从头烧 token。
- **步数预算（step budget）**：硬性 `max_iterations`，防止模型陷入「调用→失败→重试→再失败」死循环烧钱。典型值 5–10 步，超过则强制转人工或降级。

**量化/边界**：
- 死循环防护：设 `max_iterations` + 单会话 token 上限 + 单会话金额上限，三重闸门
- 长任务与 Web 请求解耦：Agent 执行是分钟级，不能挂在 HTTP 请求上 → 异步任务队列（Celery / MQ）+ 轮询或 SSE 推进度

**高频追问**：
- 「Agent 跑一半挂了怎么办？」→ checkpoint 续跑 + 幂等重放；不能幂等的步骤（如已发通知）标记为「不可重放」，人工介入
- 「怎么防止模型死循环？」→ 步数预算 + token 预算 + 失败分类（连续同类失败直接终止，不重试）

## 2. 工具层工程

**面试官真正在问**：工具是 Agent 的手。**你怎么保证这双手不会乱动？**

**必答工程细节**：
- **Tool description 就是 prompt**：描述含糊是调用失败的第一大原因。每个工具必须写清「什么时候用 / 什么时候**不要**用 / 参数含义 / 示例（Usage Examples）」。
- **工具数量与上下文成本**：工具定义常驻上下文，20 个工具可能吃掉几 K token。**动态过滤**——按当前意图只注入相关工具（通常控制在 5–10 个）。
- **副作用分级**：读 / 写 / 高危（删、转账、发布）。分级决定是否需要 dry-run、人工确认、二次鉴权。
- **幂等键**：写类工具必须支持 `idempotency_key`，重试不能产生重复副作用。
- **Schema 双重校验**：JSON Schema 只保证类型和必填；**业务合法性必须在应用侧再校验一次**（如退款金额 ≤ 订单金额）。
- **工具超时与熔断**：单个工具设超时（避免拖垮整轮），连续失败触发熔断，暂时摘除该工具。
- **MCP 传输层**：stdio（本地、单进程、低延迟）vs Streamable HTTP / SSE（远程、可多租户、支持会话）。生产远程部署通常走 HTTP。

**量化/边界**：
- 工具描述优化（补 Usage Examples）可显著降低调用错误率——**很多「模型不行」其实是「工具描述不行」**
- 工具不是越多越好：工具数增加会稀释注意力，且增加误选概率

**高频追问**：
- 「模型返回的工具名不存在怎么办？」→ 带上错误信息让模型自我修正重试（限次）→ 仍失败则降级响应，**绝不静默失败**
- 「工具和 Skill 什么区别？」→ Tool 是能力，Skill 是**流程性知识**（什么时候用、按什么顺序用、有什么坑）

## 3. 失败分类与自愈

**面试官真正在问**：出错了你怎么处理？**「加重试」是最烂的答案。**

**必答工程细节**：建立**失败分类（failure taxonomy）**，不同类别走不同路径：

| 失败类型 | 能否自愈 | 处理 |
|---|---|---|
| 参数格式/类型错误 | ✅ 可自愈 | 带错误信息回灌，让模型修正后重试（限 1–2 次） |
| 工具名不存在 / 幻觉调用 | ✅ 可自愈（限次） | 同上，连续失败则终止 |
| 业务校验失败（余额不足等） | ⚠️ 不可自愈但可明确返回 | 把业务错误结构化返回给模型，让它换策略或向用户澄清 |
| 权限不足 | ❌ 转人工 | 不重试，明确告知并升级 |
| 下游超时 / 5xx | ✅ 有限重试 | 指数退避 + 幂等键；超过上限转降级 |
| 高危操作 | ❌ 必须人工 | Human-in-the-loop，人工确认后才执行 |

**关键原则**：
- **重试预算**：全局重试次数上限 + 同类错误不重复重试（避免烧 token）
- **Self-heal 与 Human-in-the-loop 的分界**：能幂等回滚的允许自动修；不能回滚的一律人工
- **诊断与修改分离**：让 LLM 只输出**修复建议**，不直接改数据，修改动作由确定性代码执行——把概率性输出收敛成可审核的确定性动作

**高频追问**：
- 「自愈会不会把数据改坏？」→ 诊断与修改分离 + 修复建议必须经校验器/人工确认，AI 不直接写库
- 「重试会不会造成重复扣款？」→ 幂等键 + 下游幂等 + 写操作默认不自动重试

## 4. 上下文工程与成本

**面试官真正在问**：上下文是**稀缺资源**不是仓库。你怎么分配预算？

**必答工程细节**（四种操作）：
- **写入（Write）**：外部记忆 / scratchpad，把中间结论固化到上下文或外部存储
- **选取（Select）**：RAG 检索 + 工具动态加载（只注入当前需要的）
- **压缩（Compress）**：长对话摘要压缩，保留关键决策与事实，**丢弃过程性废话**
- **隔离（Isolate）**：Multi-Agent 各子 Agent 独立上下文，避免互相污染

**预算分配**（典型结构）：system prompt / 工具定义 / 历史对话 / 检索片段 / scratchpad，**每一块都要有上限**。

**成本与性能优化**：
- **Prompt Cache**：把稳定的前缀（system + 工具定义）放前面，利用前缀缓存降低重复计费与延迟。**关键：前缀必须稳定**——把动态内容（时间戳、随机数）放后面
- **裁剪策略**：滑动窗口（保留最近 N 轮）+ 关键事实固化（早期重要结论摘要常驻）
- **Lost in the Middle**：关键信息放开头或结尾，检索结果必须 rerank 后再拼

**量化**：用「每轮平均 token / 缓存命中率 / 单次任务成本」衡量；缓存命中率是可观测、可优化的核心指标。

## 5. 并发、幂等与多租户隔离

**面试官真正在问**：多用户同时用，你怎么保证不串数据？

**必答工程细节**：
- **会话隔离**：每个 session 独立上下文与状态，用 `sessionId` 做路由与隔离键（如 `ConcurrentHashMap<sessionId, ...>` 或 Redis key 前缀）。**这是多租户的第一道闸门**。
- **同一 session 并发请求**：加会话级锁或串行队列，避免两个请求交叉写同一份上下文导致状态错乱。
- **长任务与 Web 解耦**：同步 HTTP 只负责任务提交与状态查询，执行走异步 worker。
- **执行记录持久化**：每一步的输入/输出/耗时/token 落库，既是审计也是断点续跑的基础。
- **幂等**：写操作带 `idempotency_key`（通常由 会话ID + 步骤序号 + 工具名 生成），下游据此去重。

## 6. 可观测与评测

**面试官真正在问**：上线后你怎么知道它变好了还是变坏了？**说不出指标 = 没做过。**

**必答工程细节**：
- **链路追踪（trace）**：每次 LLM 调用、每次工具调用打一个 span，串成完整 trace。**出问题时能回放整条决策链**，这是 Agent 系统排障的基础设施。
- **核心指标**：
  | 类别 | 指标 |
  |---|---|
  | 效果 | 任务完成率、平均轮次、人工接管率 |
  | 稳定性 | 工具调用成功率、**失败分类分布** |
  | 成本 | 单任务 token、单任务成本、缓存命中率 |
  | 性能 | TTFT（首 token 延迟）、P50/P99 端到端延迟 |
- **离线评测**：golden dataset + 分层指标（检索层 Recall@K / MRR，生成层 faithfulness / relevance）；LLM-as-Judge 打分，但**必须用人工集校准 judge 准确率**。
- **在线评测**：A/B 实验、用户反馈（点赞点踩）、任务完成率。
- **回归测试**：**模型升级后必须跑回归**——换模型/改 prompt 是 Agent 系统最大的效果回退来源。

**关键方法论**：先做**错误分析**再定指标。打开 50 条 bad case 人工归类，看是召回不到、切片烂、还是生成乱——不同病因不同药方，一上来就换模型是最低效的做法。

## 7. 安全与权限

**面试官真正在问**：Agent 会不会变成**越权的后门**？

**必答工程细节**：
- **身份传递（最关键）**：工具调用必须**携带真实用户身份**，不能用 Agent 自身的高权限服务账号。**否则用户 A 可以让 Agent 操作用户 B 的数据**——这是 Agent 系统最经典的越权漏洞。
- **Prompt Injection**：注入源不只是用户输入，还包括**检索到的文档内容、工具返回值、网页内容**。防护：外部内容标记为「数据」而非「指令」、输出过滤、高危操作二次确认。
- **高危操作闸门**：Human-in-the-loop + 二次鉴权 + 完整执行计划展示。
- **审计日志**：谁、在什么 session、触发了什么工具、传了什么参数、结果如何，全量落盘可追溯。
- **数据边界**：检索也要做权限过滤——用户只能检索到自己有权限的文档（在检索层过滤，而不是生成后再过滤）。

## 8. 延迟与体验

**面试官真正在问**：Agent 动辄十几秒，用户能忍吗？

**必答工程细节**：
- **TTFT（首 token 延迟）**是体感的核心指标，比总耗时更重要
- **流式输出**：边生成边返回，把「等待」变成「阅读」
- **工具并行**：**无依赖**的工具调用可并行发起（parallel tool calls），有依赖的必须串行
- **超时预算拆分**：总超时 = LLM 超时 + 工具超时 × 预期步数，超预算则降级（返回已有结论 / 转人工）
- **进度反馈**：长任务分阶段返回进度，避免用户以为卡死

## 附：Agent 后端岗「加分工程判断」速查

能主动说出下面任意一条，都是明显加分项（它们都体现「默认值不是最优解」）：

1. 「自主度是**旋钮**不是开关」——生产不用纯 Autonomous
2. 「很多模型问题其实是**工具描述**问题」——先改 description 再换模型
3. 「诊断与修改**分离**」——LLM 只出修复建议，不直接写数据
4. 「先做**错误分析**再定指标」——不盲目换模型
5. 「**重试预算**比重试策略更重要」——防止死循环烧钱
6. 「工具调用必须**携带用户身份**」——否则是越权后门
7. 「**前缀稳定**才能吃满 Prompt Cache」——动态内容往后放
8. 「换模型/改 prompt 必须跑**回归**」——最大的效果回退来源
9. 「长任务必须**解耦**出 HTTP 请求」——异步 + checkpoint
10. 「上下文是**预算**不是仓库」——每块都要有上限
