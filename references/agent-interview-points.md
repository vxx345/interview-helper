# AI Agent / LLM 方向考点清单

题面命中 Agent / RAG / MCP / Multi-Agent / 知识库 / 幻觉 / Function Calling / 上下文工程 / Prompt / 评测 时读取本文件。

每个考点给出：**必答关键词**（漏了会被追问）+ **高频追问** + **常见误区**。

---

## 1. Agent 基础架构

**必答关键词**：感知（Perception）→ 规划（Planning）→ 记忆（Memory）→ 工具调用（Tool Use）→ 行动（Action）；ReAct 范式（Reason + Act 交替）；Thought / Action / Observation 循环。

**加分点**：区分「Workflow 型」和「Autonomous 型」Agent。Workflow 是人编排好流程、LLM 只做节点内的决策，可控性强、适合生产；Autonomous 是模型自主规划路径，灵活但不可控。生产环境绝大多数是前者，或者说「**自主度是一个可以调的旋钮，不是一个开关**」。

**高频追问**
- ReAct 和 Function Calling 什么关系？ → ReAct 是决策范式，Function Calling 是执行机制，前者决定「调不调、调哪个」，后者负责「怎么调、参数怎么传」。
- Agent 和 Workflow 怎么选？ → 看任务路径是否可枚举。可枚举用 Workflow，不可枚举才上 Agent。

## 2. Tool / MCP / Skill 三者区别（高频，必考）

| 维度 | Tool | MCP | Skill |
|---|---|---|---|
| 本质 | 一个可执行函数 | 工具发现与调用的**协议标准** | 一段可复用的**流程知识/指令** |
| 类比 | 一个个应用程序 | USB 接口规范 | 操作手册 / SOP |
| 解决问题 | 让模型能做事 | 让工具可以跨平台复用、即插即用 | 让模型知道怎么用工具做事 |
| 是否占上下文 | 定义常驻 | 按需发现，定义不全量常驻 | 渐进式加载，按需读取 |

**必答关键词**：MCP 是 Anthropic 提出的开放协议，解决「每个 Agent 都要为每个数据源写一遍适配」的 N×M 问题；MCP 有 Server / Client / Host 三角色，传输层支持 stdio 和 SSE/Streamable HTTP。

**常见误区**：认为 Skill 就是 Tool 的集合。Skill 的核心是**流程性知识**（什么时候用、按什么顺序用、有什么坑），不只是能力清单。

## 3. Function Calling

**必答关键词**：模型不执行函数，只**产出结构化的调用意图**（JSON）；真正的执行在应用侧；Schema（JSON Schema）既用于告知模型参数格式，也用于强校验；并行调用（parallel tool calls）。

**加分点**：参数校验要「双重」——Schema 只保证类型和必填，业务合法性（如「退款金额不能超过订单金额」）必须在应用侧再校验一次。

**高频追问**：模型返回的函数名不存在怎么办？ → 降级为重试（带上错误信息让模型自我修正）+ 兜底响应，绝不静默失败。

---

## 4. Multi-Agent 路由与调度

**必答关键词**：路由错误的两类原因（意图理解错 / 子 Agent 描述区分度不够）；四层提升手段——**元数据**（高区分度 description + Usage Examples）、**模型**（小分类器 + few-shot，比通用大模型路由更稳更快）、**反馈闭环**（混淆矩阵分析高频错分对，针对性补样例）、**架构**（分层路由，降低单层分支数）。

**加分点**：主 Agent 选错子 Agent 的补救——子 Agent 执行前做**能力自检**，发现不是自己的活就主动让贤回传，比主 Agent 事后发现成本低得多；再加一个 Reviewer Agent 做结果校验和重路由。

## 5. Agent 容错与兜底（高频场景题）

**框架**：分层法，事前 / 事中 / 事后。

- **事前：收敛动作空间**。按对话状态动态过滤可用工具，高风险工具在特定意图下直接不可见。
- **事中：强校验 + 自检**。Schema 强校验参数；执行前加 Self-Correction 步骤。
- **事后：分级处理 + 可观测**。高风险操作触发 Human-in-the-loop；低风险允许自动重试或降级返回；全链路 trace 落盘，便于复盘。

**必答关键词**：出错成本可控；幂等设计（重试不能产生副作用）；超时与重试上限（防止死循环烧 token）；灰度放量。

**高频追问**：能结合具体场景讲讲吗？ → 通用业务 Agent 的四层防御：输入校验 → 工具白名单 → 执行前 dry-run → 高危操作人工确认。

> 💡 想答到**工程实现层**（失败分类、重试预算、幂等键、诊断与修改分离、trace 指标）而非停留在概念层，转读 `agent-backend-engineering.md` 第 1/2/3/6 节。

## 6. RAG 全流程

**必答关键词**：
- **Indexing**：解析（PDF/Word/HTML 多类型文档）→ 切片（chunking，注意按语义而非固定长度）→ 向量化（embedding 模型）→ 存入向量库（同时保留原文与元数据）
- **Retrieval**：查询改写（query rewriting / HyDE）→ 混合检索（向量召回 + BM25 关键词召回，互补）→ 重排（Rerank 模型，_cross-encoder）
- **Generation**：把召回片段 + 原始问题拼进 Prompt，要求模型**基于给定材料回答并标注引用来源**

**加分点**：
- 切片是 RAG 效果的第一瓶颈，比换 embedding 模型影响更大。按标题层级切片 + 相邻 chunk 重叠，效果通常优于固定长度切分。
- 混合检索的价值：向量检索擅长语义相似，关键词检索擅长精确匹配（如型号、专有名词、代码标识符），两者召回的并集覆盖率显著更高。
- Rerank 是性价比最高的一步：召回 top50 → rerank → 取 top5 送进生成。

**高频追问**
- 多类型文档怎么存？ → 统一抽象为 `Document(page_content, metadata)`，元数据记来源/页码/章节/更新时间，向量库和原文分离存储，用 doc_id 关联。
- 知识库多大合适？ → 没有固定答案，看检索质量；超过百万级 chunk 要考虑分层索引（先检索摘要再检索细节）。

## 7. 知识库构建与持续维护

**必答关键词**：建 → 入 → 用 → 养 四阶段闭环。
- **建**：确定知识来源与权威等级，按业务域划分
- **入**：抽取 → 蒸馏 → **人工审核**（高价值知识必须过人）→ 入库
- **用**：检索 + 引用溯源（回答要能点回原文）
- **养**：定期更新、过期下线、冲突检测、用户反馈回流

**冲突知识处理**：新知识与旧知识冲突时，按三原则处理——**按权威等级**（官方 > 转载）、**按时间**（新的覆盖旧的，但要保留历史版本）、**按场景**（若两者适用场景不同，则都不是错的，补充适用条件区分）。

**错误知识防污染**：四道防线——防入（审核）、监测（定期抽样问答评测）、可纠（用户反馈入口 + 快速下线）、可溯（每条知识带来源和责任人，出问题能定位到是谁录的）。

**高频追问**：知识准确性由谁负责？ → 业务域负责人（他们最懂），技术团队提供工具和流程支持；要有明确的责任人到具体知识条目。

## 8. 幻觉治理

**必答关键词**：幻觉无法根除，只能**收敛和控制**。手段： grounding（强制基于检索材料回答）→ 引用标注（每句话可溯源）→ 低置信度时主动拒答（「材料中没有相关信息」）→ 输出校验（事实一致性检查，可用小模型或规则）。

**加分点**：把「不知道」设计成一条正常路径。大多数 RAG 系统的失败不是答错，而是材料里明明没有，模型还是硬编了一个答案。给模型一条体面的退路，比事后过滤有效得多。

---

## 9. 上下文工程（Context Engineering）

**必答关键词**：上下文是稀缺资源，不是仓库。
- **写入**：外部记忆（便签本 / scratchpad）
- **选取**：RAG 检索 + 工具动态加载
- **压缩**：长对话摘要压缩（summarization），保留关键决策和事实
- **隔离**：Multi-Agent 各子 Agent 独立上下文，避免互相污染

**加分点**：上下文窗口变大不等于可以随便塞。长上下文存在「lost in the middle」现象——中间部分的信息容易被模型忽略，所以关键指令放开头和结尾，检索结果要做 rerank 排序。

---

## 10. 评测（Eval）

**必答关键词**：离线评测 + 在线评测双轨。
- **离线**：构造评测集（golden dataset），指标含检索层（Recall@K、MRR）与生成层（忠实度 faithfulness、相关性 relevance）；用 LLM-as-Judge 打分，但要人工校准 judge 的准确率
- **在线**：A/B 实验、用户反馈（点赞/点踩）、任务完成率、平均轮次

**加分点**：先做**错误分析**再定指标。打开 50 条 bad case 人工归类，看看到底是召回不到、切片烂、还是生成乱——不同病因对应不同药方，一上来就换模型是最低效的做法。
